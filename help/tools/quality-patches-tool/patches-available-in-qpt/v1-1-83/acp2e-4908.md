# ACP2E-4908：大型目录导致Redis或Valkey内存使用率过高

ACP2E-4908修补程序修复了大型目录可能导致[!DNL Valkey]（或[!DNL Redis]）中内存使用过量的问题，这是因为在每个商店视图中为每个产品创建了单独的布局缓存条目。 安装[[!DNL Quality Patches Tool (QPT)]](/help/tools/quality-patches-tool/quality-patches-tool-to-self-serve-quality-patches.md) 1.1.83时，此修补程序可用。 修补程序ID为ACP2E-4908。 请注意，此问题计划在Adobe Commerce 2.4.10中修复。

## 受影响的产品和版本

**为Adobe Commerce版本创建了修补程序：**

* Adobe Commerce（所有部署方法） 2.4.8-p4

**与Adobe Commerce版本兼容：**

* Adobe Commerce（所有部署方法）>=2.4.8 &lt;2.4.10

>[!NOTE]
>
>该修补程序可能适用于具有新[!DNL Quality Patches Tool]发行版本的其他版本。 要检查修补程序是否与您的Adobe Commerce版本兼容，请将`magento/quality-patches`包更新到最新版本，并在[[!DNL Quality Patches Tool]：搜索修补程序页面](https://experienceleague.adobe.com/tools/commerce-quality-patches/index.html)上检查兼容性。 使用修补程序ID作为搜索关键字来查找修补程序。

## 问题

大型目录可能会导致[!DNL Redis]或[!DNL Valkey]中的内存使用过量，因为每个商店视图中的每个产品都创建了单独的布局缓存条目。

<u>重现步骤</u>：

1. 将[!DNL Valkey]（或[!DNL Redis]）配置为默认缓存后端。
1. 编辑`app/etc/env.php`并将cache.frontend.default块设置为：

   ```
   'default' => [
       'id_prefix' => '061_',
       'backend_options' => [
           'server' => 'valkey',          // your Valkey/Redis hostname
           'port' => '6379',
           'database' => '1',
           'password' => '',
           'compress_data' => '0',        // key recipe — leaves XML uncompressed
           'persistent' => 0,
           'read_timeout' => 10,
           'connect_retries' => 2,
       ],
       'backend' => 'redis',
   ],
   ```

   然后`flush: bin/magento cache:flush`。

1. 生成中等性能夹具：

   ```
   bin/magento setup:performance:generate-fixtures \
       setup/performance-toolkit/profiles/ce/medium.xml
   ```


   这将生成3个网站×3个商店组×3个商店视图，24K简单+ 640个可配置产品，33个属性集，50K订单。 使用速度快的机器预计需要10分钟。

1. 重置[!DNL Valkey] `db1`并暖机：

   ```
   valkey-cli -h <host> -n 1 FLUSHDB
   bin/magento cache:flush
   ```

1. 跨商店抓取产品页面。 构建一个示例列表并点击每个URL：

   ```
   # Build 200 random product URLs across stores 1–4
   mysql -e "SELECT CONCAT(s.code,'|',u.request_path)
             FROM url_rewrite u JOIN store s ON u.store_id=s.store_id
             WHERE u.entity_type='product'
               AND u.request_path NOT LIKE 'catalog/product/%'
               AND s.store_id BETWEEN 1 AND 4
             ORDER BY RAND() LIMIT 200;" magento > urls.txt
   
   while IFS='|' read -r STORE URL; do
       curl -s -o /dev/null "http://<base-url>/${URL}?___store=${STORE}"
   done < urls.txt
   ```

1. 观察`LAYOUT`缓存占用空间：

   ```
   valkey-cli -h <host> -n 1 --scan --pattern "*LAYOUT_FRONTEND_STORE*" | wc -l
   valkey-cli -h <host> INFO memory | grep used_memory_human
   ```


   放大抓取（或使用`large.xml`/`extra_large.xml`和真正的加载工具，如seatment/wrk），以访问客户的10K密钥/1.7 GB方案。

<u>预期的结果</u>：

启用压缩时，性能不会受到影响。

<u>实际结果</u>：

- `LAYOUT_FRONTEND_STORE` [!DNL Redis]键占用了大量空间。
- 在全新中型夹具安装中，在200次产品点击后：大约564 `LAYOUT_FRONTEND_STORE`个密钥，以及大约20 MB的`used_memory_human`（抓取前的基线约为10 MB） — 每次产品页点击约2.8个布局缓存密钥，随着独特产品访问×商店线性增长。
